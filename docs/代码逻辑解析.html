1. 系统一句话概括

把企业里各种格式的文档（pdf / doc / docx / txt / md / json / xlsx / xls / csv）上传入库， 系统自动解析 → 结构感知分块 → 向量化 → 建索引；提问时全库检索 → LLM 重排 → 结构化问答， 答案必须附带可溯源的文件名 + 行号引用，资料不足时明确拒答。

旧的比赛年报问答管道（app_streamlit.py / pipeline 等）已于 2026-10-10 清理归档，当前仓库只剩企业问答这一条链路， 两套系统互不影响。

核心设计：doc_id = 文件内容 sha1。同内容重复入库自动跳过（幂等）； 文件内容一变，hash 就变，重新入库会自动清掉旧版本产物——单文件换代，不用全量重跑。
Windows 中文路径兜底：faiss 库对含中文的路径写盘可能失败，所以先写到系统临时目录再 shutil.move 到目标位置；读取侧同样有临时目录兜底。

5. 结构感知分块（chunker.chunk_markdown）

旧的按 30 行盲切会把表格拦腰斩断、上下文丢失。新分块器按 markdown 标题层级先切节， 节内再区分表格段与文本段：

flowchart TD A["markdown 全文按行扫描"] --> B["遇标题(#~######)切节
维护章节路径 headings"] B --> C["节内划分连续段
表格行 |...| 为一段，普通文本为一段"] C --> D{"表格段?"} D -->|"是, 且整体不超限"| E["整表独立成块(原子)"] D -->|"是, 超限"| F["按行分组切分
每组重复表头行"] D -->|"否"| G["文本缓冲累积"] G --> H{"空行且已达 50% 上限?"} H -->|"是"| I["在段落边界落块(优先断点)"] H -->|"否"| J{"加该行会超限?"} J -->|"是"| I J -->|"否"| K["继续累积"] I & K --> L["每块加前缀:
【文档标题 › 章节 › 子章节】"]

块结构：{"page": 起始行, "lines": [start, end], "text": ...}，行号是原文绝对行号， 这就是最终答案能溯源到「某文件第几行」的根基。块前缀让每个块被单独检索出来时也自带章节上下文。

token 计数用本地近似（CJK 1 字 ≈ 1 token，其他 3.5 字符 ≈ 1 token）， 刻意不用 tiktoken——它首次运行要连外网下载编码表，国内环境容易卡死，而分块只需量级准确。

7. 统一模型网关（LLMClient）

能力函数实现要点
对话chat()ChatOpenAI(qwen3.7-max)，temperature=0.1，记录 token 用量
结构化输出chat_structured(schema)优先 function calling；失败自动降级 json_mode + json_repair 修复
查询向量embed_query()单条，L2 归一化（IndexFlatIP 内积即余弦），失败重试 3 次
文档向量embed_texts()批量 25 条/批（v1 上限），过滤空串 + 归一化
重排rerank_texts()裸调 dashscope.TextReRank（不经过 langchain 封装——封装层吞错）
模型版本钉死：embedding 固定 text-embedding-v1（1536 维，不支持 dimensions 参数）。 查询侧与入库侧走的是 LangChain 不同的参数路径，v3 不显式钉死维度时两侧维度会不一致（1024 vs 1536）—— 这是踩过的真实坑。今后换 v3 必须全量重建向量库。

9. 关键设计决策速查

决策理由
doc_id = 内容 sha1幂等入库 + 文件更新自动换代，单文件维度管理
每文档独立 faiss 文件单文件增删重建互不影响，无需全库重索引
结构感知分块 + 表格原子化表格数值问答精确的关键；超长表按行分组并重复表头
块带章节路径前缀孤立块检索时保留上下文，提升召回相关性
向量分与重排分 0.7/0.3 加权融合重排分数语义更准为主，向量分兜底防重排异常
结构化输出双通道function calling 失败自动降级 json_mode + json_repair，提高可用性
绝对行号贯穿全链解析→分块→检索→引用，答案可溯源到原文行
解析器统一 ParseResult所有格式收敛为 markdown + meta，分块层零感知格式差异
